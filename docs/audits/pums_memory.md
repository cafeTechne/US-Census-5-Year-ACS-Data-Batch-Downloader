Generated by `python scripts/pums_memory_benchmark.py` on 2026-11-08 (PLAN_ROUND_14 workstream C; PLAN_ROUND_11 R2/F3). Synthetic PUMS-shaped person files only; nothing was downloaded.

## Environment

- Platform: Linux-7.0.0-42-generic-x86_64-with-glibc2.43 (x86_64), 16 CPUs, 123 GiB RAM
- Python 3.14.4, numpy 2.5.4, pandas 3.1.1
- Peak RSS: kernel high-water mark (VmHWM, the value `resource.getrusage().ru_maxrss` reports), one fresh subprocess per phase and chunk size. The weights and tabulate subprocesses read the file, then reset the high-water mark (`/proc/self/clear_refs`), so their peak is that phase on top of the resident frame.
- Baseline (interpreter, numpy, pandas, census.pums imported): 279 MiB

## Scaling and practical limit

A least-squares line through the end-to-end peaks gives peak = 275 MiB + 2,829 bytes x rows. With 2 GiB left for the operating system, the rows that fit with these columns are:

| Machine RAM | Rows (person records) that fit | California-sized states (1.9M rows) |
| :--- | ---: | ---: |
| 16 GiB | 5,211,831 | 2.7 |
| 128 GiB | 47,722,509 | 25.1 |

These are for the needed columns plus the 80 replicate weights. Each extra numeric column read adds 8 bytes per row (float64 after conversion) and each extra text column more (pandas strings); `columns=None` reads all 280+ columns of a real file and multiplies the frame several-fold (the PumsMemoryWarning above 200 MB). The figures exclude the download step: `fetch_pums` holds the compressed response in memory once while writing it to the cache (one zip, hundreds of MB for the largest states).

## Findings and recommendation

- Memory scales linearly with rows, at about 2,829 bytes per person record for this column set; the largest state (about 1,900,000 records) peaked at 5.28 GiB.
- Chunk size does not bound memory (every chunk is kept until the frame is concatenated) and does not change any result: estimates, SEs and the frame are bit-identical across chunk sizes. Smaller chunks only lower the transient parser buffer.
- The peak comes from tabulation, which holds the frame, the 81-column float64 weight matrix and per-statistic temporaries at once; reading alone peaks lower.
- A 16 GiB machine handles any single state with the needed columns; the owner's 128 GiB machine holds about 25 California-sized files in one process (all states together are about 16 million 5-year person records).
- Recommendation: keep the Round 10 design (full state files on demand, needed columns only); no streaming rewrite is warranted. For many states, tabulate state by state and combine, or read with `columns=[...]` and `filter=` to keep only the rows and variables needed.
